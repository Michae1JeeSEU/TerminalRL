## Budgets and execution lifecycle

This new evaluation has a fresh ledger initialized once by `prepare`: evaluation45,000s, preflight900s, archive900s; compute-stop45,900s and total46,800s. It does not alter or reset the completed online-v2 ledger. Each arm has the same fixed21,600s (6h) process cap; a case therefore has at most43,200s of arm time plus the shared evaluation allowance for overhead. These caps do not change per-callback planning budgets.

The frozen `run_subprocess` computes the minimum of phase allowance and requested cap. Before every H or L launch, the driver therefore requires at least21,601s remaining, passes cap21,600s, and checks the resulting receipt's timeout is exactly21,600s. If an equal full cap is unavailable, it returns to the primary instead of shortening L's budget. One evaluation phase owns both case threads; each subprocess uses `parallel=True` accounting. On an error/partial result, no later new cell is deliberately started after the stop is observed; already running cells retain their outputs. Parent exit pauses the same new ledger, and `run.started.json` prevents retries/reset.

The per-callback algorithms remain unchanged: candidate6s, per-aircraft32 / global1,024 attempts, hint3s, CP8s, soft30s, watchdog60s. H/L use cumulative active candidate work. Features/inference inside `next(catalogs)` consume this fixed candidate clock; selection is excluded. Lower search/CP work cannot be attributed solely to smarter ranking.

For initial monitoring only, extrapolating the previous medium H/L pair by10 gives about10,535s (2.93h); multiplying the high case by its36/24 initial-count ratio gives about15,800s (4.4h). The two-case parallel estimate is roughly4.5h, not a runtime guarantee. The primary updates estimates and heartbeat timing from actual progress; no sleeping monitor is built into the driver.

## Saved boundaries, terminal and replay

The driver calls the original `world.advance(absolute_boundary, normal, settle_only_at_end=True)` at5,10,…,600s. It retains the same physical integration and scheduling triggers, practical-runtime1s telemetry plus event/junction frames, and lightweight OnlineObserver. There is no profiler, renderer or new stream-restore mechanism. World state frames remain in the existing in-memory recording implementation.

- Every completed5s boundary saves actual quality, holding-energy observations, cumulative costs/dispatch data, identity, CPU and execution scope. A progress JSON publishes case/arm/PID, actual simulated time, last completed boundary, callback count, elapsed wall and phase for ETA.
- Full checkpoints are written at t0 and60,120,…,600s. An independent terminal checkpoint is written when a partial/invalid stop requires one. This reduces cumulative-history copying relative to the old every5s checkpoints; H/L share the rule. Historical60s I/O timing is therefore not a strict causal control.
- A failed/invalid world or an incomplete boundary does not publish that boundary as complete. Independent terminal quality/time is saved, while result.time remains the last completed boundary. `terminal_costs` and all-callback aggregation retain work through the actual terminal even when it is later than the shared comparison boundary.
- The original ReplayBundle writer receives actual world states/events/committed trajectories and all scheduler decisions. Tentative predictions remain separate. No human acceptance flag is set.
- Full wall through each completed boundary starts at driver job entry, including frozen imports/source verification; an additional job-finished wall records work through replay export. Phase/callback/dispatch costs retain their original definitions. No gain is assumed from changing the measured I/O boundary.

`summarize` publishes each case's largest completed boundary shared by H/L, independent terminal observations, existing quality differences, all replay decision/dispatch aggregation, and saved60s quality/landing/energy trends. No trend is fabricated for an uncompleted boundary. Cohorts remain inside the original quality dictionaries. A missing terminal is explicit, not replaced by the last common state. Current artifacts, logs, process exit codes, watchdog limits and stage markers are retained.
